# Scoping & audit — the detail behind the AGENTS.md one-liners

Deep-dives: `docs/architecture/exchange-scoping.md`, `sharepoint-selected.md`, `audit-findings-and-remediation.md`, `resource-access-and-permission-tester.md`.

- **Scope-aware audit risk.** `score_application` reads `AppPermissions.mail_scopes` (empty map = org-wide, so an unresolved probe never under-reports). A **legacy AAP** verdict is its OWN finding + migrate Fix — same reduced weight, but never the `SCOPED_VIA_RBAC` healthy one. Badges: `web-rs/components/scope_badge.rs`.
- **No built-in scoping (Rule 24) is visibility, never a scope.** `audit::is_unscopable_privileged` is the ONE classifier (Rule 24, the row badge, the picker note, the wizard warning): risk-weighted Graph app permission, not a directory read, not owned by Rules 11/12, no toolkit mechanism. Advisory and score-free; each grant's Conditional Access `NetworkLock` is filled per grant by the runner (`apply_network_locks`) — unreadable policies are `Unknown`, never "no lock", and only a transient read is the `ConditionalAccess` gap. Copy never calls a safeguard "scoped". Usage (`GrantUsage`, from one static-table KQL query spawned beside scoring) never degrades the run; only `NotSeen` is evidence about the grant (a seen call is one it *could* have authorized). The network lock (Conditional Access tab, `commands::network_lock`) is created report-only and changed only through `toolkit_lock_for` (our name prefix + exactly this SP + the exact shape), re-read live before every write; named locations it creates are untrusted. The Teams meeting access policy (C3) is a generated script only (`core::teams_meeting_policy`: single-quoted literals with `'` doubled, GUID ids, never `-Global`); nothing is run or read.
- **Expiring grants (Rule 25) are SP tags, never a scheduler.** `azapptoolkit:grantExpiry:v1|resource|role|date` on the holding SP (`audit::grant_expiry`, parsed as untrusted; a grant expires at the end of its UTC day). The audit reads them from the run's SP index and names roles through the cached resource-SP read, never the run's resolver (a dead resource never degrades the run); the `RevokeExpiredGrants` Fix acts only on the confirmed pairs (`AuditItem.expired_grants`), re-reads tags and held grants live, revokes, drops only the revoked grants' declarations in one PATCH, and clears the tags; a re-grant made after the date is kept. Every revoke path prunes unheld expiries and a downgrade carries the expiry over (`every_app_role_revoke_prunes_unheld_expiries`).
- **Admin-unit scoping (C1, Rule 26) assigns a role, never a tenant-wide one.** `scoping::admin_unit::DIRECTORY_WRITE_MAPPINGS` is the one table (Graph `User`/`Group`/`Device.ReadWrite.All` → User/Groups/Cloud Device Administrator, the tenant-wide read each needs, and the disclosures the review must show). The apply assigns at `/administrativeUnits/{id}` (built in the Graph client), ensures tenant-wide read, and strips the tenant-wide write only when the unit wasn't just created, holds members of the right kind and its rule isn't paused; a tenant-scope same role or Global Administrator voids the limit. Direct, active assignments only.
- **Mailbox AND SharePoint permissions live on TWO resources each — carry the resource, never the bare value.** Only Graph's are confinable, so a value-keyed shortcut silently widens access. Permissions travel as `audit::ResourcePermission`; every gate uses the POSITIVE `is_scopable_{exchange,sharepoint}_resource_permission` / `scope_kind_for`. The value-only forms are **deleted** and `repo_invariants.rs` fails if one returns.
- **`Sites.Selected` reach is knowable only from the site side.** No reverse `appId → sites` lookup exists, so the Resource Access sweep and the per-app "Sites this app can reach" panel share ONE tenant index; `AppSiteAccessDto::from_sweep` is the single projection (cached ⇒ backend-side, fresh ⇒ frontend), and an empty list means "no grants" only when `is_complete()` (not cancelled, no failed sites, and not stopped at the 5000-site cap — a capped sweep is cached *with* `truncated` set, never as complete).
- **Sub-site Selected scopes are a SECOND mechanism, and their reach is not enumerable at all.** `Lists.`/`ListItems.`/`Files.SelectedOperations.Selected` → `ScopeKind::SharePointItem` (Graph-only, like the site gate); the body is **`grantedToV2`**, never the site endpoint's `grantedToIdentities`. A URL is resolved *before* granting and checked with `selected_scope_accepts` — fail closed, never one level up. Both apply paths **declare** the appRole (`declare_graph_role`) before assigning it: the Permissions tab renders declarations, so an undeclared assignment shows nowhere. Sub-site 403s key to their OWN capability (`sharepoint_selected_items`). No sweep exists: grants are verified per URL, and empty means "this resource has no grants", never "this app has none". The per-app list is the app's own record: one `azapptoolkit:spItem:v1|…` tag per grant on the app registration (`commands::sharepoint_item_scopes`), written by `grant_selected_item_access` when it has an `object_id`, read back with live status (`Unreadable` is never `NotGranted`), parsed as untrusted (strict id shapes; ids go into Graph paths), written full-collection under a per-app `single_flight`. Remove re-verifies the entry is this app's, and that `object_id` is `app_id`'s registration, before deleting; the Permission Tester's revoke deletes application grants only (`not_an_app_grant`). No role change in place (v1.0 has none): remove, then add.
- **SharePoint input is shape-checked at the graph client boundary.** `site_lookup_path` parses the pasted URL (`url::Url`), rebuilds the path from its segments and refuses `:` / encoded `/ \ : .` segments, bad hosts, credentials and ports; `url_host_and_segments` (the item resolver) applies the same segment rule; every site, drive, list, item and permission id the client splices into a path runs `validate::require_path_segment` (`trust.rs::every_client_path_splice_is_shape_checked`, which holds every `/{name}` a Graph, ARM or Key Vault client method splices into a `format!` path to the same check); the grant commands admit `read`/`write` only and check that `object_id`/`sp_object_id` carry the grant's `app_id` (`principal_mismatch`), as the Exchange managed-identity grant does before its first write.
- **AAP migration is guarded, not mechanical.** `RestrictAccess` only (a `DenyAccess` blocklist inverts), one batch per **app**, policies deleted only once every grant they confined is re-scoped **and** both mailbox resources resolved; an unverifiable set fails closed. Planner: `azapptoolkit-exchange::aap` (pure, tested).
- **Scoped grants reuse shared cores.** Exchange + SharePoint grant scoped access *before* stripping org-wide, so a failure never strands the principal. Each then reports what is STILL org-wide (Exchange `still_held_orgwide`; SharePoint `residual_orgwide_reach`, keyed by `(resource, value)` — the strip is Graph `Sites.*` only, so a SharePoint Online `Sites.*` or a Graph `Files.*.All` survives it), and a warned result stays on screen and keeps its Fix. The Exchange scope and its backing mail-group use two distinct per-tenant patterns (`scope_name_for`/`group_name_for`) covering **every** scoping path, resolved via `load_tenant_defaults`. Membership changes **don't** invalidate caches.
- **Repointing a management scope is an explicit action, and fail-closed.** `ensure_management_scope` is create-only; `set_management_scope_filter` is the sole filter mutator, and Exchange applies it to **every** role assignment on that scope. A filter is rewritten only once proven a pure `MemberOfGroup` OR-chain — the planners refuse rather than fall back.
- **Unified "Grant access" wizard.** One button per principal (`ScopeWizard`): permissions → access → grant. `mechanism` is `Some(kind)` only when every cart item is an Application permission of the **same** `ScopeKind`; anything else is org-wide. Adding a mechanism touches core (`ScopeKind` + its arms + `scope_kind_for` + a catalog entry), the wizard's `ScopeMode` + `mode_options` rows (the compiler then demands every exhaustive match), and some copy, cart state and the "Scope…" row gates the compiler can't see — the list is in `audit-findings-and-remediation.md`.
- **Audit remediation (one-click "Fix")** — only for findings with a safe, existing mutation (additive/reversible qualifies); the handler **re-resolves live state**. Which are scorer-attached, which reuse an existing core, and the `DisableSignIn` post-pass are in the audit deep-dive.
- **The audit also scores SP-only principals (no local app registration) — and those rows are NOT bulk targets.** `AuditItem.principal_kind` drives routing; SP rows' Fixes call the SP-only cores, **never** `remediate_scope_*` (which `get_application` first → 404), render no checkbox, and are excluded from select-all.
- **Security tab = findings-first workbench: one controller, read-only posture strip.** Filtering has exactly two homes (Findings accordion + All-apps `audit_severity`); `BulkActionBar` is the single home of bulk command-calling; **no bulk admin consent (`BulkAction::Grant`) on audit surfaces** — the operator's own AuditLog.Read.All consent on the strip is not that (pinned by `groups.rs::no_audit_surface_offers_bulk_admin_consent`). The `scoped_mailbox` matcher asymmetry is load-bearing (see `frontend-workspace.md`).
- **Audit scoring rule** — implement in `azapptoolkit-core::audit` with a table-driven test citing the legacy PowerShell `file:line`. A rule that shifts ranking needs a CHANGELOG note — operators watch these scores.

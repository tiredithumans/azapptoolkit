## Second-pass findings (gap slices)

These 52 findings come from a completeness critic that named lenses the 26 first-pass slices had not applied. Six gap finders then swept those lenses: shared cancel and throttle state across long-running runs, error codes as the operator actually sees them, the launch cold path, updater and install formats per OS, the support log, and the desktop crate's inline test oracles. Every finding was verified against the source; 14 were narrowed by the verifier (marked "partially") and the two high findings were re-verified by a second pass. Counts by severity: 2 high, 28 medium, 22 low.

### Concurrency and shared cancel/throttle state (gap-cancel-flag-sharing)

#### F440 · medium · effort M · audit_cancel is shared by the read-only audit, every bulk write and the AAP migration, and the UI can run them concurrently, so any Cancel button stops all of them
`apps/desktop/src-tauri/src/commands/bulk.rs:127` · confirmed
**Problem.** The docstring at bulk.rs:125-134 says the audit and bulk loops "never run at once", so one flag covers both. That premise is false: views are keep-alive, `BulkActionBar` gates only on its own `busy`, and the audit controller only on `scanning`. All ten bulk commands and the AAP migration claim `audit_cancel`, and `cancel()` stamps the current generation, so either Cancel button stops every run on the flag. The verifier lowered it from high to medium: a stopped bulk run names its unattempted remainder and a cancelled audit is never cached, so the harm is a wrong-target cancel plus a misleading coverage caveat.
```rust
pub fn cancel_bulk(state: State<'_, AppState>) {
    state.audit_cancel.cancel();
}
```
**Proposal.** Minimal: add `bulk_cancel` and `migration_cancel` flags, point `cancel_bulk` and the `bulk_*` claims at them, and pin the command-to-flag mapping in `repo_invariants/cancel.rs`. Robust: return the generation from `claim()`, emit it as `run_id` in the first progress event, and add `cancel_run(run_id)` so each Cancel stops exactly its own run. The verifier notes only the run_id variant also stops two bulk bars cross-cancelling and fixes the interleaved `bulk-progress` rows every mounted bar receives.

#### F442 · medium · effort M · sweep_cancel is shared by the site sweep, Key Vault sweep, mailbox probe and per-app site panel, all of which can run concurrently from always-mounted panels; one panel's Cancel aborts the others
`apps/desktop/src-tauri/src/commands/permission_tester.rs:443` · confirmed
**Problem.** The docstring claims the mailbox probe and site sweep "never run concurrently from the UI", yet resource_access/mod.rs:19-20 says all panels stay mounted with independent busy signals. The site sweep, Key Vault sweep, mailbox probe and per-app site panel all claim `sweep_cancel`, and all four Cancel handlers call `cancel_resource_sweep`. Cancelling a 20-second mailbox probe therefore aborts a multi-minute site or vault sweep, which is deliberately not cached, so the whole scan is lost with a coverage caveat the operator never aimed at it. Two site sweeps (Sites tab plus app panel) can also run at once with no single-flight, so the tenant walk is paid twice and their progress events interleave.
**Proposal.** Split into `site_sweep_cancel`, `keyvault_sweep_cancel` and `mailbox_probe_cancel` with their own commands, or adopt the run_id design from F440, and fix the docstring plus resource-access-and-permission-tester.md:14-15. Wrap `sweep_site_permissions` in `state.single_flight(&sweep_cache_key(..))` with a post-acquire cache re-check; the verifier notes single_flight is documented for read-through caches, and joining is safe here only because a cancelled first run is never cached.

#### F441 · medium · effort S · GraphClient has a single throttle_observer slot, so concurrent fan-outs on one tenant overwrite each other's tracker and ThrottleGuard::drop clears whichever run's observer is installed
`apps/desktop/src-tauri/src/commands/throttle.rs:141` · confirmed
**Problem.** `GraphClient` holds one observer slot; `set_throttle_observer` overwrites it and `clear_throttle_observer` clears it unconditionally, which is what `ThrottleGuard::drop` calls. Every fan-out (audit, bulk, site sweep, DR backup) attaches to the shared per-tenant `Arc<GraphClient>`, so a second run silently replaces the first run's tracker and its 429s halve the wrong cap. When either guard drops first, it removes the other run's observer, leaving a live fan-out at a fixed cap with no back-off, the pre-adaptive behaviour the throttle was added to fix. The verifier notes the transport still honours Retry-After, so this degrades back-off rather than correctness.
```rust
throttle_observer: parking_lot::RwLock<Option<Arc<dyn ThrottleObserver>>>,
```
**Proposal.** Make the slot multi-observer (`RwLock<Vec<Weak<dyn ThrottleObserver>>>`, notify every live Weak, remove only your own tracker on drop via `Weak::ptr_eq`), or at minimum make `clear_throttle_observer` a compare-and-clear with `Arc::ptr_eq` and log a displaced observer. Add a transport test that attaches two observers, asserts both see a 429, and checks that dropping one guard leaves the other attached.

### Error codes to screen and degraded network (gap-error-code-to-screen)

#### F465 · medium · effort M · `unauthorized` (client 401, including the CAE "re-auth needed" path) renders as bare "unauthorized (401)" with no action; the three ui_hints tell the operator to sign out, contradicting the in-place recovery design
`apps/desktop/web-rs/src/state/errors.rs:157` · confirmed
**Problem.** A Graph 401, including a CAE claims challenge the silent re-mint could not satisfy, reaches `report_command_error_for` and falls through to a plain toast reading `unauthorized (401)`. The remedy the transport itself names ("surfaces to the caller to re-auth") already exists as the top-bar Refresh token handler, which falls back to `reauthenticate` on a dead session. Meanwhile the Key Vault, ARM and Exchange `Unauthorized` hints say "Sign out and back in", contradicting auth-and-consent.md:101 ("Force re-auth in place, never make the user sign out"). `unauthorized` is deliberately excluded from `REAUTH_FATAL_CODES` so fan-outs keep going; that rationale is about loops, not the screen.
**Proposal.** Extract the shell's refresh handler into `Session::spawn_refresh_token()`, and in the sink add a branch for `code == "unauthorized"` that toasts "Your access token was rejected" with a Refresh token action. Reword the three hints and `premium_feature_err` to "use Refresh token (next to Sign out), then retry", the wording exchange/error.rs already uses for its 403 hint, and add a GUI test beside tests/gui/reauth.rs. Do not add the code to `REAUTH_FATAL_CODES`.

#### F467 · medium · effort S · ARM, Key Vault and Exchange reads burn minutes on a firewalled host before a cause-less network error; only Graph has a connect budget
`crates/azapptoolkit-arm/src/client.rs:38` · partially (verifier: Log Analytics `query` is a POST and ARM/KV writes are non-idempotent, so they get one attempt of about 2 min; the ~247 s figure holds only for ARM/KV GETs and every Exchange cmdlet)
**Problem.** The Graph client sets `.connect_timeout(10 s)` with a comment explaining that a blackholed host otherwise burns the whole 60 s ceiling once per attempt. The ARM, Log Analytics, Exchange and Key Vault builders set only `.timeout(60 s)` (120 s for Log Analytics), and the SSO metadata probe uses `unwrap_or_default()`, which falls back to a client with no timeout at all. On an egress allow-list that admits only graph.microsoft.com, an ARM or KV read retries three times for roughly four 60 s attempts plus back-off, with no `CancelToken`, before the cause-less `network` error of F463.
```rust
let http = reqwest::Client::builder()
    .user_agent(concat!("azapptoolkit/", env!("CARGO_PKG_VERSION")))
    .timeout(Duration::from_secs(60))
```
**Proposal.** Add `.connect_timeout(Duration::from_secs(10))` to the four builders and the SSO probe, replacing `unwrap_or_default()` with the `expect` the others use. Pin it with a repo_invariants source scan asserting every `reqwest::Client::builder()` outside azapptoolkit-auth is followed by `.connect_timeout(`; the verifier notes core has no reqwest dependency, so a shared builder there would add a dependency edge.

#### F462 · medium · effort S · `throttled` error message leaks Rust `Option` Debug formatting ("retry after Some(30)s" / "retry after Nones") and never says to wait
`crates/azapptoolkit-core/src/http_error.rs:76` · confirmed
**Problem.** Both the `http_error_enum!` macro and the hand-written `ExchangeError` format the arm with `{retry_after_secs:?}`, the Debug formatter for `Option<u64>`. `ui_error_from!` copies `err.to_string()` into `UiError.message`, and `DetailLoadError` and the toast render it verbatim, so after three exhausted Retry-After waits the operator reads `throttled (429); retry after Some(30)s`. No frontend site branches on `throttled`, and the two GUI fixtures use "Too many requests", a string the backend never produces, so no test can see the leak.
```rust
#[error("throttled (429); retry after {retry_after_secs:?}s")]
Throttled { retry_after_secs: Option<u64> },
```
**Proposal.** Format the arm with thiserror's extra-args form, e.g. `.retry_after_secs.map_or("a moment".to_string(), |s| format!("{s} s"))`, so no manual Display is needed for the macro or `ExchangeError`; the verifier suggested this refinement. Add an error-conformance test asserting the message contains neither "Some(" nor "None", and switch the two GUI fixtures to the real backend string.

#### F463 · medium · effort M · Network errors drop the cause: `err.to_string()` on reqwest 0.13 yields only "error sending request for url (...)", hiding DNS/timeout/TLS/proxy at all six sites and in the retry log
`crates/azapptoolkit-graph/src/client/transport.rs:571` · partially (verifier: README has no proxy/TLS guidance to match a symptom against, and core has no reqwest dependency, so `is_timeout()`/`is_connect()` cannot live there)
**Problem.** reqwest 0.13.5's Display writes only the kind plus ` for url (...)` and never the `source()` chain. All six `Network(err.to_string())` sites (graph transport.rs:571 and 585, arm/transport.rs:60, keyvault/client.rs:196, exchange transport.rs:188 and 196) and `AuthError::Http`'s `#[error("http: {0}")]` discard the cause, so DNS failure, connect timeout, TLS interception and proxy 407 all read identically on screen. Worse, `with_retries` logs only label, attempt and retry_after, so the cause is not in the log either; only Exchange's hand loop logs `?err`.
**Proposal.** Add a dependency-free `describe_error_chain(e: &dyn std::error::Error) -> String` in core that joins Display of `e` and each `source()` (hyper already says "dns error", "connection refused", "invalid peer certificate"), use it at the six sites and in a manual Display for `AuthError::Http`, and log it in the retry warn line. Classify timeout versus connect only at the call sites that hold the concrete `reqwest::Error`. Unit-test with a refused localhost port.

### Updater, install formats and OS paths (gap-updater-install-format-platforms)

#### F488 · high · effort S · Linux release leg builds on floating `ubuntu-latest`, so the AppImage/.deb require glibc >= 2.38 and cannot start on Ubuntu 22.04 / Debian 12 / RHEL 9 despite 'runs on most distributions'
`.github/workflows/release.yml:105` · confirmed, re-verified
